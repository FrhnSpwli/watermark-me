## 1. Background

WatermarkMe v0.2 expands the product from a privacy-first watermarking workflow into a broader privacy-first document preparation workflow.

The core idea from the recovered specification remains:

> A document should not always mean one physical file.

A real-world identity document may have multiple sources, such as the front and back of an ID card. A PDF may contain many pages while the user only needs a subset. Users need to select, reorder, convert, and watermark that content without altering private originals or downloading and uploading intermediate files again.

v0.1 primarily treated a document as one original file. v0.2 introduces a logical document containing one or more persisted source files, plus a browser-local composition layer in which one image or one PDF page is an independently selectable item.

## 2. Product Principles

The v0.2 design center is:

```text
Choose exactly what needs to be shared
→ put it in the correct order
→ convert it into the right format
→ watermark it for the intended recipient
→ share the safer copy
```

The following are hard requirements:

- WatermarkMe remains privacy-first rather than becoming a generic converter.
- Persisted originals remain immutable and privately stored.
- Database and Storage authorization is enforced by RLS and Storage policies, not UI filtering.
- Existing v0.1 documents and Storage objects remain compatible.
- Generated conversion and watermark outputs remain browser-local by default.
- No Supabase service-role key, database password, or private server credential is exposed to frontend code.
- Heavy PDF, conversion, and archive functionality is lazy-loaded where practical.
- Scope remains limited to JPG/JPEG, PNG, and PDF.

## 3. v0.2 Target Flow

The final implemented flow is:

```text
Private Stored Sources
        ↓
Document Composer
  select / exclude / reorder
        ↓
Browser Conversion
        ↓
ConversionResult Blob artifact(s)
       ↙                         ↘
Direct Download          In-memory Handoff
                                 ↓
                         Watermark Editor
                                 ↓
                         Final local download
```

Conversion output does not need to be downloaded and re-uploaded before watermarking. Neither intermediate conversion output nor final watermark output is uploaded or persisted by this workflow.

## 4. Document and Source Architecture

v0.2 changes the mental model to:

```text
Document = logical user-owned container
Document → one or more source files
```

The relationship is:

```text
auth.users
    └── public.documents
            └── public.document_files
                    ├── source 1
                    ├── source 2
                    └── source N
```

### `documents`

`public.documents` remains the logical document. Its `user_id` is the ownership authority. The v0.1 file columns (`mime_type`, `file_size`, and `storage_path`) remain as compatibility metadata and mirror the first ordered source so older application paths continue to work. They were not destructively removed in v0.2.

### `document_files`

The implemented source table contains:

```text
id              uuid primary key
document_id     uuid → public.documents.id on delete cascade
original_name   text
mime_type       image/jpeg | image/png | application/pdf
file_size       1 byte through 10 MiB
storage_path    text unique
sort_order      non-negative integer
created_at      timestamptz
updated_at      timestamptz
```

`(document_id, sort_order)` is unique. Ownership is derived through the parent document rather than duplicated on each source row.

### Storage layouts

Both layouts are valid:

```text
Legacy: USER_ID/DOCUMENT_ID/original.ext
v0.2:   USER_ID/DOCUMENT_ID/FILE_ID/original.ext
```

The source-path validation trigger verifies that the owner and document path segments match the parent document. The nested file segment must be a UUID. Existing legacy objects are not moved merely to adopt v0.2.

### Persisted source order versus Composer order

`document_files.sort_order` controls persisted source-management order. Arbitrary page/item ordering in Composer is session-local and must not update `document_files.sort_order`.

## 5. Multi-file Management

Phase 12 implements:

- single-file upload with the existing behavior;
- multi-select upload as separate logical documents;
- multi-select upload combined into one named logical document;
- an editable logical document name independent of source filenames;
- source addition using a new nested immutable Storage path;
- source removal with protection against removing the final source;
- source move-up/move-down ordering;
- compatibility-mirror updates after persisted source order changes;
- per-file failures for separate uploads;
- rollback attempts when Storage succeeds but metadata creation fails.

New source `original_name` values retain the selected file names. Legacy backfilled sources use the existing logical document name because no separate historical filename metadata existed.

Upload operations use `upsert: false`; originals are never overwritten. Combined upload and source-add workflows remove newly uploaded objects when a later metadata operation fails. A failure after a Storage deletion is reported explicitly as a partial-delete condition rather than silently presented as success.

## 6. Document Composer

The protected Composer route is:

```text
/documents/:documentId/compose
```

The in-memory `ComposerItem` union has two variants:

```text
image-file
pdf-page
```

Every item has stable source-scoped identity, a source file ID/name, MIME metadata, initial order, current Composer order, and selection state. PDF page items additionally contain zero-based page index, user-facing page number, dimensions, and rotation.

Final behavior includes:

- all successfully loaded items selected by default;
- selection, deselection, and recovery of excluded items;
- one global order across images and PDF pages;
- pointer reordering;
- keyboard-accessible **Move earlier** and **Move later** controls;
- active image/PDF-page preview;
- per-source loading and failure isolation;
- source browser and selected-order views;
- a controlled not-ready state when no item is selected;
- session-local state that is reset when the Composer session is lost.

The Composer does not generate output by itself, persist page records, or mutate original source metadata.

## 7. PDF Preview Architecture

PDF pages are processing units, not persisted database rows. The Composer uses lazy-loaded `pdfjs-dist` with a separate worker asset to:

- inspect page count, dimensions, and rotation;
- create one `pdf-page` item per page;
- render thumbnails progressively as they approach the viewport;
- render the active page responsively;
- bound preview pixel density;
- cancel active renders and source work when views change or unmount.

PDF.js page proxies are cleaned after inspection/rendering, render tasks can be cancelled, and document proxies are destroyed when their owning Composer session releases them. `pdf-lib` is reserved for PDF manipulation/export rather than page-preview rendering.

## 8. Conversion Engine

The conversion engine is independent of React presentation and Supabase persistence. It accepts:

- ordered `ComposerItem` values;
- a requested target MIME type;
- an injected private-source `Blob` resolver;
- an optional `AbortSignal`;
- an optional progress observer.

It returns a `ConversionResult` containing one or more ordered `ConversionArtifact` objects. Every artifact has a non-empty `Blob`, controlled MIME type/extension, and the IDs of Composer items represented by that artifact.

The current Composer selection and `composerOrder` are authoritative. A private source is resolved at most once per conversion operation and reused through an operation-local cache. Cancellation is typed, progress observer failures cannot corrupt output, and partial arrays are not returned as successful results.

The engine does not create database rows, Storage objects, signed-URL history, or conversion history.

## 9. Supported Conversion Matrix

The authoritative as-built matrix is:

| Selected content | PDF | PNG | JPEG |
| --- | --- | --- | --- |
| Single JPEG | one PDF | one PNG | one JPEG pass-through artifact |
| Single PNG | one PDF | one PNG pass-through artifact | one JPEG |
| Multiple JPEG/PNG images | one combined PDF | one PNG per selected image | one JPEG per selected image |
| Selected PDF pages | one selected/reordered PDF | one PNG per selected page | one JPEG per selected page |
| Mixed image + PDF pages | one combined PDF | unavailable | unavailable |

Zero selected items expose no conversion target. A single JPEG defaults to PNG, a single PNG defaults to JPEG, and other supported selections default to PDF. Compatibility options are derived from current selected content; unsupported targets are not offered.

## 10. Image Conversion Rules

- JPEG → PNG uses browser Canvas encoding. UI guidance explicitly states that changing container format cannot restore detail already lost through JPEG compression.
- PNG → JPEG composites transparency onto deterministic white before JPEG encoding and displays alpha-loss/lossy warnings.
- JPEG output uses the centralized encoder quality configured by the implementation.
- PNG → PNG and JPEG → JPEG pass the exact source `Blob` through without decoding or re-encoding.
- Image decoding respects browser orientation metadata where supported.
- Input Blobs and persisted source objects are never mutated.

For a mixed JPEG/PNG image batch, only items whose MIME type differs from the target are re-encoded.

## 11. PDF Composition

`pdf-lib` implements PDF output.

### Images → PDF

Each image becomes one A4 portrait or landscape page according to image orientation. The image is contain-fitted, centered, and drawn inside a fixed 24-point margin without stretching or clipping.

### PDF pages → PDF

Only selected pages are copied. Native PDF pages are copied directly rather than rasterized, and selection/reordering is preserved exactly.

### Mixed image + PDF pages → PDF

Images create image-backed pages while selected PDF pages are copied natively. Output page order follows the exact mixed Composer order. The result remains a browser-local PDF Blob.

## 12. PDF Raster Outputs

Selected PDF pages may produce PNG or JPEG artifacts through PDF.js:

- one artifact is produced per selected page;
- artifact order follows Composer order;
- only selected pages are rendered;
- default rendering uses 2× scale, capped at 4096 pixels on the longest edge;
- JPEG rendering uses a deterministic white page background;
- PDF documents and Canvas backing stores are released after the operation;
- render, source, and post-parse work observes cancellation.

This browser-local raster path is not offered for a mixed image/PDF-page selection.

## 13. Conversion Output UX

The Composer output panel provides:

- target options derived from the implemented matrix;
- single/multiple output shape messaging;
- JPEG lossy/alpha and PDF rasterization warnings;
- real item-stage progress;
- cancellation, retry, and interaction locking;
- immediate invalidation of a result when document, selection, order, or target changes;
- output size and generated filename summaries;
- one direct download for a single artifact;
- explicit individual downloads for multi-output artifacts;
- one **Download all as ZIP** action.

No multi-output conversion starts an uncontrolled cascade of automatic downloads. Download object URLs are temporary and revoked after use. JSZip is loaded only when archive preparation is requested.

### Filenames

Output names are normalized, stripped of traversal/path characters, bounded in length, and protected from reserved/empty basenames. Multi-image outputs derive names from each source and replace its extension. Case-insensitive collisions receive deterministic suffixes such as `_002`. PDF-page image artifacts use the sanitized logical-document base plus ordered numeric suffixes. ZIPs contain only generated artifacts, not originals, metadata JSON, Storage paths, UUID manifests, or signed URLs.

## 14. Multi-output Image Behavior

For more than one selected image:

```text
PDF  → one combined PDF
PNG  → one ordered PNG per selected image
JPEG → one ordered JPEG per selected image
```

Each artifact remains traceable to its Composer item. Same-format artifacts are passed through, mismatched formats alone invoke Canvas conversion, every artifact has an individual download, and one user action packages the complete ordered set into a ZIP.

## 15. Converter → Watermark Integration

Phase 16 connects conversion to the existing Watermark Editor without persistence:

```text
ConversionResult
→ session-owned in-memory registry
→ opaque handoff identifier in navigation state
→ Watermark Editor
→ final in-memory result
→ download or ZIP
```

Generated artifact bytes are authoritative in generated-handoff mode. The editor does not rerun conversion, re-download an intermediate file, upload it, refetch the stored original merely to watermark it, or silently fall back to Storage if the handoff is unavailable.

Persisted-source mode remains separate: a direct watermark request resolves exactly one authoritative `document_files` source, creates short-lived private access for that source, and selects image/PDF handling from source MIME metadata. Two or more persisted sources remain blocked from the single-source watermark flow.

## 16. Generated Image Watermarking

A generated PNG or JPEG is decoded directly from its in-memory Blob and enters the existing Canvas watermark engine. If the image was a transparent PNG converted to JPEG, the already-converted white-background JPEG is the actual watermark input.

The image watermark renderer creates a separate PNG result. Consequently, a watermarked generated JPEG is truthfully named and typed as PNG. The original conversion artifact remains unchanged.

## 17. Generated PDF Watermarking

A generated PDF enters the existing `pdf-lib` watermark engine directly:

- the input stays PDF;
- no preview-raster reconstruction is used;
- every generated page is preserved;
- Composer page order remains unchanged;
- the watermark is fitted to each actual page and applied to every page;
- the final result is a separate browser-local PDF.

## 18. Batch Image Watermarking

A homogeneous generated PNG[] or JPEG[] result creates one explicit batch session:

```text
ordered conversion artifacts
→ one shared purpose/recipient/appearance configuration
→ every artifact processed in order
→ ordered PNG watermark results
→ one Watermarked ZIP
```

The editor previews one batch artifact at a time with previous/next navigation. It never silently selects `artifacts[0]` and ignores the rest. Progress reflects real completed artifact counts, and final filenames use deterministic ordered suffixes.

## 19. Watermark Purpose Experience

The six implemented purposes are:

- Job Application
- Bank Verification
- Property Rental
- University Admission
- Insurance
- Other

The first five require a recipient/organization and generate:

```text
ONLY FOR
RECIPIENT / ORGANIZATION
DD MON YYYY
```

`Other` allows optional recipient data and requires non-empty custom watermark text. Generated text is editable, manual edits are preserved until reset, and reset restores current purpose/recipient/date text.

Image, generated-image batch, persisted PDF, and generated PDF flows share purpose semantics. Available appearance controls are opacity, rotation, relative size, and nine fixed positions from top-left through bottom-right. The session date is used consistently for visible text and output filename generation.

## 20. Handoff Lifecycle

- Generated Blobs are held only in JavaScript memory.
- Navigation state contains only an opaque handoff ID.
- The registry is bound to the authenticated owner and logical document.
- One active handoff is retained; creating another replaces the previous reference.
- Explicit discard and owner change clear the active handoff.
- Refresh/navigation without the registry state intentionally cannot restore generated bytes.
- Missing or expired handoffs show a controlled temporary-unavailable state and a route back to Composer.
- A handoff cannot resolve for another account or another document.

No handoff data is stored in `localStorage`, `sessionStorage`, IndexedDB, Cache Storage, Supabase Database, or Supabase Storage.

## 21. Privacy and Security Model

### Database

- `documents` and `document_files` use RLS.
- Source SELECT/INSERT/UPDATE/DELETE policies require an owned parent document.
- Parent ownership is checked by the database; frontend filtering is not authorization.
- Foreign keys and uniqueness/non-negative constraints enforce source integrity.

### Storage

- The `documents` bucket is private.
- The allowed MIME types are JPEG, PNG, and PDF, with a 10 MiB source limit.
- Storage SELECT/INSERT/DELETE policies require the authenticated owner path and Storage owner ID.
- Both legacy and nested source layouts remain valid.
- There is intentionally no application Storage UPDATE policy for originals.

### Generated content and frontend configuration

- No generated document row or source row is created.
- No intermediate or final generated artifact is uploaded.
- No generated artifact is persisted through browser storage APIs.
- Frontend configuration is limited to `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`.
- A service-role credential must never appear in frontend code.

## 22. Original Immutability

Original immutability is a hard invariant:

```text
Composer   → does not modify originals
Conversion → does not modify originals
Watermark  → does not modify originals
```

Generated files are independent browser-local Blobs. Composer ordering does not rewrite persisted source ordering. Conversion and watermarking do not update compatibility metadata.

Source-management actions are the only v0.2 workflows intentionally allowed to change persisted source state: add, reorder, remove, rename the logical document, or delete the logical document. Those operations remain owner-scoped and never transform an original in place.

## 23. Legacy Compatibility

Phase 11 backfilled each then-existing v0.1 `documents` row into one `document_files` row using its real MIME type, size, and unchanged legacy Storage path with `sort_order = 0`.

A later repair migration addressed the historical Phase 11 → Phase 12 migration window by adding metadata only for documents with zero source rows. It reused real legacy paths and created no Storage objects.

The application normalizes legacy compatibility metadata into one source only when explicit source rows are absent. When `document_files` rows are available, they are authoritative. The direct single-source watermark resolver supports:

- legacy JPEG/PNG;
- legacy PDF;
- nested v0.2 JPEG/PNG;
- nested v0.2 PDF.

A persisted document with two or more sources is guarded rather than silently watermarking its first source.

## 24. Error Handling and Unsupported Inputs

Controlled user-facing states exist for:

- missing document or source metadata;
- unavailable private access;
- unsupported MIME type;
- corrupt or empty image;
- corrupt PDF;
- encrypted/password-protected PDF;
- missing/invalid PDF page;
- decode, render, conversion, encoding, ZIP, or watermark failure;
- intentional cancellation;
- expired generated handoff.

Errors avoid exposing signed URLs, Storage paths, SQL details, provider secrets, or raw stacks. Current selection/order is retained where recovery is practical. Password removal and format broadening are not supported.

## 25. Resource Lifecycle

Resource ownership and cancellation paths are explicitly implemented and covered by repository regression:

- object URLs are revoked;
- `ImageBitmap.close()` releases decoded bitmap resources;
- Canvas backing dimensions are cleared after conversion;
- PDF.js page proxies are cleaned;
- PDF.js documents are destroyed;
- render tasks and private source work observe cancellation;
- `AbortSignal` propagates through conversion, private source reads, PDF parsing/page enumeration, and generated preview decoding;
- download URLs are revoked;
- handoff references clear on replacement, discard, or owner change.

These controls do not constitute mathematical proof of zero browser-memory leakage. Repeated real-browser stress remains the appropriate acceptance method and is documented separately.

## 26. Performance and Lazy Loading

- Composer and Watermark Editor are route-level code-split screens.
- PDF preview and its worker are separate from the initial route.
- PDF composition, PDF rasterization, and image conversion adapters are dynamically loaded by target path.
- `pdf-lib` processing remains separated where the architecture permits.
- JSZip is loaded only for ZIP generation.
- PDF thumbnails render progressively near the viewport.

Phase 17 verified that the historical ineffective image-watermark dynamic import was removed without pulling document-processing paths into the initial app route. Exact hashed filenames and transient chunk metrics are release evidence, not permanent specification limits.

## 27. Accessibility and Responsive Requirements

v0.2 requires:

- pointer reorder plus keyboard **Move earlier**/**Move later** alternatives;
- keyboard-operable item selection;
- meaningful labels and accessible button names;
- reachable target, conversion, cancellation, download, and handoff controls;
- visible focus treatment;
- usable Composer and Watermark layouts on mobile, tablet, and desktop;
- no critical horizontal overflow that hides primary actions.

This specification does not claim formal WCAG conformance.

## 29. Acceptance Criteria

v0.2 is acceptance-complete only when all applicable repository and live/manual evidence confirms:

- legacy v0.1 images and PDFs still work;
- logical documents expose one or more valid source records;
- source add/remove/reorder and final-source protection work;
- Composer image/PDF items can be selected and reordered without persistent source-order mutation;
- selected PDF pages and mixed items preserve exact Composer order;
- every supported conversion-matrix path produces valid output;
- multi-image PNG/JPEG conversion includes every artifact;
- individual downloads and one controlled ZIP work with safe unique names;
- mixed image/PDF composition remains PDF-only and preserves order;
- generated conversion output can continue directly to watermarking;
- image-batch watermarking processes every artifact with shared settings;
- generated PDF watermarking preserves native PDF pages/order;
- direct persisted image/PDF watermarking does not regress;
- stale conversion and watermark results are invalidated;
- refresh fails generated handoff safely without Storage fallback;
- account changes clear the previous owner's handoff;
- originals and source metadata remain unchanged in pure compose/convert/watermark flows;
- generated output remains browser-local;
- RLS and private Storage isolation hold in both account directions;
- no service-role credential is exposed;
- resource cancellation/cleanup paths work under repeated stress;
- responsive and keyboard-only acceptance passes;
- no open BLOCKER or HIGH privacy, security, correctness, or performance finding remains.

Automated tests provide repository evidence; they do not substitute for live Supabase or browser acceptance. The detailed read-only SQL, two-account matrix, output inspection, network checks, stress cases, and responsive/keyboard steps live in [`PHASE17_RELEASE_ACCEPTANCE.md`](PHASE17_RELEASE_ACCEPTANCE.md).

## 30. Non-goals

The recovered specification explicitly kept WatermarkMe from becoming a universal conversion or editing platform. v0.2 does not add:

- DOCX, XLSX, PPTX, HEIC, SVG, TIFF, TXT, or RTF conversion;
- OCR or AI document recognition;
- image enhancement or background removal;
- camera scanning;
- server/cloud conversion infrastructure;
- collaboration;
- saved conversion history or persisted generated versions;
- watermark history;
- public sharing or expiring links;
- digital signatures;
- PDF password removal;
- advanced PDF editing or arbitrary layer editing;
- mixed image + PDF-page output to PNG/JPEG.

Future features require an explicit later roadmap decision and must not weaken the v0.2 privacy model.
